- The Product -> Offer locking helper now fails closed before its first query unless the active database connection is already inside a transaction.
- The known production checkout, direct resolver integration tests and concurrency workers already satisfy this precondition. A future internal caller cannot silently execute ineffective `FOR UPDATE` reads in autocommit mode.
- This is an application-level guard, not a database constraint: direct database writers still remain outside the serialization guarantee.

## Checkout identity preflight — 28 October 2026

- Checkout now rejects missing, non-string, blank, whitespace-padded or duplicate purchase IDs before opening its database transaction.
- This prevents one committed purchase row from satisfying multiple corrupt cart entries during duplicate-key or ambiguous-commit recovery.
- Invalid carts remain intact for explicit user recovery; no reservation or purchase event is attempted.
- Ledger service resolution now occurs only after this preflight, so invalid carts cannot initialize wallet/ledger dependencies.
- Durable buyer-bound request-key idempotency remains a separate schema or signed-client-token design task.

## Empty-cart dependency boundary — 29 October 2026

- Added an executable regression proving an empty cart is rejected before the application container resolves `WalletLedgerService`.
- The empty-cart path opens no transaction, preserves the empty cart and dispatches no purchase event.
- This extends the existing source contract for checkout preflight ordering without changing production code, schema, wallet behavior or public contracts.

## Checkout request-exception context — 29 October 2026

- Known checkout `RequestException` failures are now rethrown unchanged after logging instead of being reconstructed from only their message.
- The original exception identity, code, previous cause and stack remain available to the existing error boundary while the public type and message stay unchanged.
- Focused coverage proves the failure occurs before transaction, reservation or purchase-event dispatch and leaves the session cart intact.

## Checkout quantity preflight — 29 October 2026

- Checkout now requires every session-cart quantity to be a positive native integer before resolving the ledger or opening a database transaction.
- Missing, zero, negative, fractional and string values are rejected instead of being aliased later by integer casts during ambiguous-commit recovery.
- Invalid carts remain intact for explicit recovery; no reservation or purchase event is attempted.
- Normal cart creation already stores an integer quantity, so this closes corrupt or legacy direct-session input without changing the supported cart contract.

## Sequential checkout retry preflight — 29 October 2026

- After validating stable IDs and quantities, checkout now performs a read-only lookup for an already fully committed matching purchase set before resolving the ledger or entering payment/inventory work.
- A complete match clears the stale session cart and reuses the committed purchases without transaction or reservation replay. Partial or conflicting rows continue to fail closed through the existing recovery boundary.
- This protects a normal sequential retry after commit/session-clear ambiguity. It does not serialize two simultaneous first submissions and does not replace a durable buyer-bound request key or transactional event outbox.
